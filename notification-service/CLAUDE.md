# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Scope: this file covers `notification-service` only. See the root `CLAUDE.md` for monorepo-wide architecture and how this service fits into the event flow.

## What this service owns

Sends transactional notifications (welcome emails, verification codes) in response to RabbitMQ events from `identity-service`, via a channel-adapter design: `internal/domain/notification.Sender` is the channel-agnostic interface, and `internal/infrastructure/notification/email` is its one implementation today (SMTP). A second channel (SMS, web-push) would be a new sibling package under `internal/infrastructure/notification/` implementing the same `Sender` interface — no interface redesign needed, see the `Sender`/`Message` shape in `internal/domain/notification/sender.go`. It has **no database, no HTTP API, and no `cmd/api`/`cmd/worker` split** — `cmd/main.go` is the only binary, it's a pure consumer, and (unlike identity-worker/restaurant-worker) it *is* started directly by the root `compose.yaml`.

Consumes (see `internal/infrastructure/messaging/rabbitmq_consumer.go`):
- `email.verification_created` → `EmailVerificationCreated` handler
- `user.registered` → `UserRegistered` handler
- `restaurant.ready_for_review` → `RestaurantReadyForReview` handler — from restaurant-service, not identity-service; sent to `ADMIN_EMAIL`, not the event's own subject, since this is an internal admin notification rather than a transactional email to an end user.
- `restaurant.approved` → `RestaurantApproved` handler — from restaurant-service; sent to the payload's own `Email` field (the restaurant's contact email, denormalized onto the `restaurant.approved` domain event by `Restaurant.Approve()` itself, guaranteed set by the checklist invariant — see restaurant-service's `CLAUDE.md`), not `ADMIN_EMAIL` — this is an owner-facing notification, not an admin one.

All four consumed events are published via an outbox now, not best-effort: the two `identity.events` via identity-service's own outbox — see identity-service's `CLAUDE.md` — and `restaurant.ready_for_review`/`restaurant.approved` via restaurant-service's, same as every other event that service raises. See restaurant-service's `CLAUDE.md`.

## Commands

Run from inside `notification-service/`:
```bash
go run ./cmd      # or `air -c .air.toml` for live reload, matches the dev container
go test ./...
go test ./... -run TestName
```
No database or `.env.test`/compose.test.yaml integration needed here — tests are pure unit tests against mocked `notification.Sender`/`notification.TemplateLoader`/`notification.EventDispatcher` interfaces (see `tests/application/notification/*_test.go`), including for the RabbitMQ consumer (`tests/infrastructure/messaging/rabbitmq_consumer_test.go` calls `messaging.Run` directly against a fake `messageSource` + a fake `amqp.Acknowledger`, not a live broker — see the architecture bullet below for why `Run` takes its dependencies as plain parameters instead of being a method).

## Architecture specifics

- **Channel-adapter design**: `internal/domain/notification.Sender` (`Send(msg Message) error`, `Message{To, Subject, Body}`) is deliberately channel-agnostic — `Subject` is used by the email adapter and would simply go unused by a channel that doesn't have one (SMS, web-push). The concrete SMTP implementation lives under `internal/infrastructure/notification/email/`, so a second adapter has an obvious sibling location (`internal/infrastructure/notification/sms/`, etc.) without touching the interface. `TemplateLoader`/`EventDispatcher`/`EventHandler` (also in `internal/domain/notification/`) were already channel-agnostic before this design existed — they operate on raw named events and rendered strings, not email specifically.
- **Same consumer reliability pattern as restaurant-service's worker**: dead-letter exchange (`email_dlx`), manual ack, QoS prefetch 1, linear-backoff retry via `x-retry-count` header, discard after `MaxRetryAttempts = 3` — all still shared in spirit. `ensureConnected` here checks both `c.conn.IsClosed()` and `c.channel.IsClosed()` before reconnecting (a real bug fix: a channel can die from a channel-level AMQP exception while the underlying connection stays open, and a conn-only check would then loop failing forever instead of recovering) — restaurant-service's copy (`internal/infrastructure/messaging/rabbitmq_consumer.go` there) has since received the same fix, ported from here. The two are independent copies of the same design, not shared code, so if touching retry/DLX/reconnect logic in either file, check whether the other should change too.
- **Handler wiring in `internal/container/container.go` uses literal routing-key strings** (`dispatcher.Register("user.registered", userRegistered)`, etc.), matching search-service's `container/worker.go` — previously indexed into `messaging.Exchanges[...]` by position, which silently bound the wrong handler to the wrong routing key if that slice's order ever changed; fixed 2026-09-02.
- **Templates are selected dynamically by role for `user.registered`**: `internal/application/notification/user_registered.go` builds template filenames as `fmt.Sprintf("%s_welcome_email_subject.html", payload.Role)` / `..._body.html`, so adding a new user role requires adding matching `<role>_welcome_email_subject.html` / `<role>_welcome_email_body.html` files under `internal/infrastructure/notification/email/templates/` — there's no fallback/default template, an unrecognized role fails validation before rendering is attempted.
- **`email_verification_created` templates are fixed-named** (`email_verification_subject.html` / `email_verification_body.html`), not role-based.
- **Templates are rendered via `text/template.ParseFiles`, not `html/template`** — deliberately, despite the `.html` filenames: every template is actually plain-text email body/subject content (no real markup), so `text/template`'s lack of HTML-escaping is correct here (auto-escaping would be pointless overhead, not a safety net, since the output is never rendered as HTML). Path resolution is relative — `container.go` hardcodes `"internal/infrastructure/notification/email/templates"`, so the binary must be run with the service directory as its working directory, which is what `go run ./cmd`, `air`, and the Dockerfile all do.
- **Config is read directly from `os.Getenv` in application handlers** (`APP_NAME`, `SUPPORT_EMAIL`, `TOKEN_EXPIRY_MINUTES`), not just in `container.go` — keep this in mind when adding template variables, since there's no central config struct being passed down.
- **SMTP sending** (`internal/infrastructure/notification/email/smtp_sender.go`) is a thin wrapper over `net/smtp.SendMail` with `PlainAuth` — no retry/circuit-breaking of its own; delivery retries happen one level up, at the RabbitMQ consumer/DLX level. The raw message is hand-assembled (`From`/`To`/`Subject`/`MIME-Version`/`Content-Type: text/plain; charset="UTF-8"`/`Content-Transfer-Encoding: 8bit` headers, then a blank line, then the body) — `net/smtp.SendMail` does none of this for you, it just sends whatever `msg` bytes it's given. If adding a new header, add it here explicitly; the `From`/`MIME`/charset headers were previously missing entirely (silently breaking sender display and garbling the emoji/em-dash characters the templates actually contain) until a bug pass fixed it — don't reintroduce that gap when touching this function.
- **Structured logging via `internal/infrastructure/observability/logger`** (ported from restaurant-service's `logobs` package, same `NewLogger`/`WithContext`/`FromContext` API): `cmd/main.go` builds the logger with `NewLogger("notification-worker")` and seeds it into the consumer's `ctx` via `WithContext` before calling `messaging.Run(ctx, app.Consumer, app.Dispatcher)`; `rabbitmq_consumer.go`'s reconnect/retry-exhausted/republish-failure paths read it back via `FromContext(ctx)` instead of stdlib `log`. Unlike restaurant-service/identity-service, there's no `middleware.go` here — this service has no HTTP API, so there's no Gin router to inject a request-scoped logger into; the only context this logger ever rides is the one worker context set up once in `cmd/main.go`.
- **`Run`/`runOnce` are package-level functions, not methods on `*RabbitMQConsumer`** — a deliberate design, not an oversight: they take a `messageSource` interface (`GetMessages`/`Republish`) as a plain parameter instead of reading it off a receiver, the same shape as `io.Copy(dst, src)` or `http.Serve(listener, handler)` — the consume/dispatch/retry loop is an algorithm over "anything that can hand me deliveries and let me republish one," not an intrinsic behavior of one specific connection object. `*RabbitMQConsumer` still satisfies `messageSource` and is what production code (`cmd/main.go`) passes in. This shape exists specifically so `tests/infrastructure/messaging/rabbitmq_consumer_test.go` can call `messaging.Run(ctx, fakeSource, dispatcher)` directly with no real broker — the alternative (a `source` field on `RabbitMQConsumer`) would've required either an unexported-field-setting test living inside `internal/` (breaking this repo's `tests/`-mirrors-`internal/` convention) or a test-only exported constructor cluttering the production API; this design has neither cost.

## Testing conventions

Unlike identity-service/restaurant-service, there's no `tests/testutil/db.go` or fixtures — everything here is mocked at the interface boundary (`notification.Sender`, `notification.TemplateLoader`, `notification.EventDispatcher`). When adding a handler or infra piece, follow the existing pattern of a local `mockX` struct implementing the relevant domain interface plus a `var _ notification.X = (*mockX)(nil)` compile-time assertion, rather than reaching for a mocking library.

`tests/infrastructure/messaging/rabbitmq_consumer_test.go` follows the same local-fake pattern but needs two extra fakes beyond a `mockDispatcher`, since `messaging.Run` exercises real concurrency and RabbitMQ's own ack model: a `fakeSource` (`messageSource`'s `GetMessages`/`Republish`, backed by a plain `chan amqp091.Delivery` the test sends into and a slice recording `Republish` calls) and a `fakeAcknowledger` (`amqp091.Delivery`'s own `Acknowledger` interface field — `amqp091-go` is explicitly designed to support this, see its doc comment on `Acknowledger`) so `msg.Ack`/`msg.Nack` can be observed without a real channel. Both are guarded with a `sync.Mutex` since they're written from the goroutine running `messaging.Run` and read from the test goroutine; assertions use a short polling `waitFor(t, timeout, cond)` helper rather than a fixed `time.Sleep`, since the retry path's `time.Sleep(retryCount+1 seconds)` inside `runOnce` makes a fixed wait either flaky or needlessly slow depending on which one is picked.
