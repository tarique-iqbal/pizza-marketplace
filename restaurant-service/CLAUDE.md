# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Scope: this file covers `restaurant-service` only. See the root `CLAUDE.md` for monorepo-wide architecture and how this service fits into the event flow.

## What this service owns

Restaurant records and their onboarding checklist. It is the only service that talks to `postgres-restaurant` and the OpenCage geocoding API. It does **not** implement the outbox pattern (see root `CLAUDE.md`) — its `cmd/worker` is a plain RabbitMQ *consumer*, not an outbox relay.

Routes (behind Traefik, JWT-protected + owner-only):
- `PATCH /restaurants/:id/contact` — updates email/phone/website, full replace (`internal/interfaces/http/handlers/contact_handler.go`). `Email` and `Phone` are required; `Website` is optional and cleared when omitted. `Phone` is checked against a custom `phone` validator tag (`internal/interfaces/http/validation/validators.go`) — a loose digits/`+`/spaces/hyphens/parens pattern requiring at least 6 digits, not a strict E.164 check, since real-world input (e.g. `+49 40 12345678`) isn't E.164-compliant.
- `PATCH /restaurants/:id/address` — updates address, re-geocoding only if it changed (`internal/interfaces/http/handlers/address_handler.go`).
- `PATCH /restaurants/:id/delivery` — updates pickup/delivery-type/radius/fee/minimum-order (`internal/interfaces/http/handlers/delivery_handler.go`).
- `POST /restaurants/:id/payout-details` — submits payout bank details (account holder, IBAN, BIC, bank name) as a new `pending` record awaiting verification, returns `201 Created`; `409 Conflict` if a `pending` record already exists (`internal/interfaces/http/handlers/payout_handler.go`, method `CreatePayout`). `POST`, not `PUT`/`PATCH`: every successful call inserts a brand-new row rather than converging to a fixed state, so this isn't idempotent and doesn't fit PUT's create-or-replace-at-known-URI contract — it's a "submit for review" action, not a resource replacement. Note the route says `payout` while the checklist item it completes is `ChecklistPayment` (`"payment"`) — that's deliberate, not a typo: the checklist step name predates this feature and represents the onboarding step ("have they set up payment"), while `payout` is the more precise term for what's actually stored (the restaurant's payout destination, as opposed to how a customer pays).
- `PUT /restaurants/:id/payout-details` — replaces the `pending` submission's fields in place (method `UpdatePayout`), full replace (all four fields required). Deliberately `PUT`, not `PATCH` like `address`/`delivery` — even though those two are also full-replace, this one is conditional on a `pending` record existing rather than an unconditional "resource at this URI is now exactly this," so it's called out with a different verb rather than following those two by default. `404 Not Found` (`restaurant.ErrNoPendingPayout`) if there is no `pending` record — including when only an `active` record exists. Unlike every other mutating command in this file, `UpdatePayout` does **not** call `restaurantRepo.Update`: `ChecklistPayment` is already true from `Create`, and no `restaurants` column changes, so touching that table here would just be a spurious `UpdatedAt` bump. There is still no way to cancel/withdraw a `pending` submission — that was deliberately removed (see git history around 2026-08-04) in favor of this edit endpoint and hasn't been reintroduced.
- `PATCH /restaurants/:id/opening-hours` — replaces the weekly schedule (method `UpdateOpeningHours`), full replace like `address`/`delivery`. Each weekday (`Monday`...`Sunday`) holds a list of `internal/domain/restaurant.DayRange{Open, Close string}` in `HH:MM`; an empty/nil list means closed that day. Multiple ranges per day are supported (e.g. lunch/dinner split). Ranges are calendar-day-bound — `Close` must be later than `Open`, no crossing midnight within one range — so a place open past midnight represents that as two entries (e.g. `monday: 15:00-23:59` plus `tuesday: 00:00-03:00` for the carryover) rather than one range spanning two days.
- `GET /restaurants/:id/pizzas` — lists the restaurant's pizzas (`internal/interfaces/http/handlers/pizza_handler.go`, method `ListPizzas`). Excludes `status: archived` pizzas by default; `available`/`unavailable` both show. No checklist gate — an owner can see their (possibly empty) menu regardless of onboarding status. No single-pizza `GET /:id/pizzas/:pizzaId` exists yet.
- `POST /restaurants/:id/pizzas` — creates a pizza (method `CreatePizza`). **Checklist-gated**: 403 (`restaurant.ErrChecklistIncomplete`) unless all six checklist items are complete — see the updated checklist bullet below, this is the first code path that actually calls `Checklist.IsCompleted()`. `CreatePizzaRequest` optionally accepts `toppingIds` — if given, `CreatePizza` validates existence only (`ValidateToppingSelections`, `internal/application/restaurant/topping_selection.go`) then calls `pizza.SetToppingIDs(...)` (which itself rejects duplicates — see below) to set the pizza's *default* toppings in the same call. See below for why existence is the only check — pricing is not involved.
- `PUT /restaurants/:id/pizzas/:pizzaId` — full replace of a pizza's own fields (`name`, `image`, `isVegetarian`, `status`, `sortOrder`, `toppingIds`) (method `UpdatePizza`). No checklist gate, no `description` field. `isVegetarian`/`status` omitted from the request body keep their existing value rather than resetting — see below for why there's no `DELETE` and `status: archived` is the retirement path instead. `toppingIds` follows the same "omitted keeps existing value" rule, but at the slice level: `input.ToppingIDs == nil` (JSON key absent) leaves the pizza's toppings untouched entirely — no repo calls, no validation; a *present* value, even `[]`, means "replace with exactly this" (same existence/no-duplicate validation `CreatePizza` uses) and clears toppings to none if empty. This nil-vs-empty distinction is why `ToppingIDs` stays a plain `[]uuid.UUID`, not a pointer — Go's `encoding/json` already leaves an absent slice field `nil` while an explicit `[]` unmarshals to a non-nil empty slice, so the zero-cost distinction was already there for the taking. Response also reports the pizza's real current prices and toppings regardless of what this call changed — see the full-current-state bullet below for why.
- `PUT /restaurants/:id/pizzas/:pizzaId/prices` — sets a pizza's per-size prices (method `SetPizzaPrices`). Upsert-and-deactivate, not a hard replace: sizes included in the request become active at the given price; sizes previously priced but omitted become `isActive: false`, not deleted — see below. Response also reports the pizza's real current toppings, even though this call never touches them — see the full-current-state bullet below for why.
- `PUT /restaurants/:id/topping-prices` — sets the restaurant's own price for a topping a *customer* can add on top at order time (method `SetToppingPrices`, `internal/interfaces/http/handlers/topping_price_handler.go`) — unrelated to a pizza's own default toppings, see below. Upsert-only, not a full replace: toppings included are priced/re-priced; toppings priced earlier and omitted from the request stay priced, untouched — there is currently no way to un-price a topping through this endpoint. `extraPrice` must be `1`–`3` inclusive — see the validation-split bullet below for where and why that's enforced.

## Commands

Run from inside `restaurant-service/`:
```bash
go run ./cmd/api      # HTTP API (or `air -c .air.toml` for live reload, matches the dev container)
go run ./cmd/worker   # RabbitMQ consumer for identity events — NOT started by compose.yaml, run manually
go test ./...
go test ./... -run TestName
```
Tests are integration-style against real Postgres (see root `CLAUDE.md` for `compose.test.yaml`); no mocked-DB path. Needs `.env.test` populated like `.env.example` (including `OPENCAGE_API_KEY`).

Migrations (`internal/infrastructure/migrations/*.sql`, golang-migrate) define `restaurants`, `pizza_sizes`, `payout_details`, `pizzas`, `pizza_prices`, `toppings`, and `topping_prices`. There is no `pizza_topping_items` table — a pizza's topping selections live directly on `pizzas.toppings` (`JSONB NOT NULL DEFAULT '[]'`), a plain array of topping IDs; see below for why. `pizza_sizes` has a Go model (`internal/domain/restaurant/pizza_size.go`) but **no test fixture and no repository/application code beyond `PizzaSizeRepository.List`** (used only to validate a `SizeID` reference in `SetPizzaPrices`) — its `code`/`label`/`sort_order` catalog-display columns from the original design draft were never added; schema is still ahead of the code for that part. `toppings` is the same kind of global, migration-seeded catalog as `pizza_sizes` (12 seed rows) — also no fixture, tests query the seeded rows directly — and, like `pizza_sizes`, carries no price: `topping_prices` is where a restaurant's own price for a customer-requested *extra* topping lives, a separate concern from a pizza's own defaults (see below).

## Architecture specifics

- **`cmd/worker` here is the `restaurant-worker` from the root architecture diagram**: it consumes `restaurant.initiated` off RabbitMQ (published by `identity-service`'s outbox) and creates the local `Restaurant` row. Wiring: `internal/container/worker.go` registers `events.RestaurantInitiated` against routing key `restaurant.initiated` on an in-process `EventDispatcher` (`internal/application/restaurant/events/dispatcher.go`); `internal/infrastructure/messaging/rabbitmq_consumer.go` pulls messages and calls `dispatcher.Dispatch`. To handle a new inbound event type, add a handler implementing `restaurant.EventHandler` and register it in `container/worker.go` plus add its routing key to `messaging.Exchanges["identity.events"]`.
- **Consumer reliability**: manual ack, QoS prefetch 1, a dead-letter exchange (`restaurant_dlx`) wired to the main queue, and in-process retry via `x-retry-count` header (linear backoff, `MaxRetryAttempts = 3` before the message is discarded). This is a different reliability mechanism from identity-service's outbox — don't conflate the two when reasoning about delivery guarantees.
- **Restaurant onboarding is checklist-driven**: `internal/domain/restaurant/checklist.go` defines six required items (`basic`, `contact`, `address`, `delivery`, `payment`, and `ChecklistOpeningHours` — value `"openinghours"`, matching the other five items' single-word-no-separator convention) and `Checklist.IsCompleted()`. `RestaurantInitiated` (the `restaurant.initiated` handler) marks `basic` complete on creation; `UpdateContact` marks `contact` complete; `UpdateAddress` marks `address` complete; `UpdateDelivery` marks `delivery` complete; `CreatePayout` marks `payment` complete; `UpdateOpeningHours` marks `ChecklistOpeningHours` complete. Every item now has a handler, so `IsCompleted()` is reachable — **`CreatePizza` (`internal/application/restaurant/commands/create_pizza.go`) is the first, and so far only, code path that actually calls it**, gating pizza creation on full onboarding. It still doesn't gate anything about the restaurant itself: **no code transitions `restaurants.status` to `active` or publishes `restaurant.launched`** — the launch flow described in the root README/architecture doc remains unimplemented here. There used to be a seventh item, `contract` (legal partnership agreement), but it was removed before any endpoint was built for it — if that concept is reintroduced later, follow the `UpdateContact`/`UpdateAddress`/`UpdateDelivery`/`CreatePayout`/`UpdateOpeningHours` pattern (ownership check → mark checklist item → mutate → persist → map response).
- **`internal/application/restaurant/queries/` exists, `commands/` isn't the only application-layer directory anymore**: `ListPizzas` (backing `GET /:id/pizzas`) is the first read-only use case in this service, and it got its own `queries/` package rather than living in `commands/` — once a directory is literally named "commands," a pure read inside it is a naming lie. This is a `restaurant-service`-specific choice, not a monorepo-wide convention: `identity-service` has no such split at all (e.g. its read-only `find_by_id.go` sits flat alongside `register_customer.go`/`register_owner.go` in `internal/application/user/`) — don't assume the two services need to match. Any future read-only use case in `restaurant-service` goes in `queries/`; anything that mutates goes in `commands/`.
- **Every GORM model in this service now uses GORM's own timestamp management**: all models tag `CreatedAt`/`UpdatedAt` with `gorm:"...;autoCreateTime"`/`gorm:"...;autoUpdateTime;default:null"`, and no model has a `WithUpdated()` method — `Restaurant`/`PayoutDetails`/`PizzaSize` were the last holdouts on a manual `WithUpdated()` pattern and were converted to match `Pizza`/`PizzaPrice`/`Topping`/`ToppingPrice`'s existing convention, `WithUpdated()` deleted entirely (no references remain anywhere in the codebase). This also closed a real, previously-open bug: `Restaurant.UpdatedAt`/`PayoutDetails.UpdatedAt` used to get silently set by GORM on `Create()` too, despite the manual-pattern intent — GORM auto-manages any field literally named `UpdatedAt` regardless of what the model author wants, unless explicitly told not to. **One exception**: `PizzaPriceRepository.ReplacePrices`'s bulk `ON CONFLICT DO UPDATE` upsert doesn't work with bare `autoUpdateTime` — GORM decides client-side, before the SQL is built, whether to include a value for a nil `UpdatedAt`, so with `default:null` it omits the column from `VALUES` entirely and that omission propagates into `EXCLUDED.updated_at` too, leaving even genuinely-updated rows `NULL`. `ReplacePrices` works around this with a manual `UpdatedAt` assignment before the upsert `Create` call — the one deliberate exception to "let GORM handle it" in this feature. Plain `.Update()`/`.Updates()` calls (not upserts) don't have this problem.
- **The pizza menu is a set of separate aggregates, never embedded in `RestaurantResponse`**: `internal/domain/restaurant/pizza.go`, `pizza_price.go`, `pizza_size.go`, and `topping.go`/`topping_price.go` (the latter two no longer `pizza_`-prefixed, see below), each with its own repository in `internal/domain/restaurant/` / `internal/infrastructure/persistence/`. `pizza_sizes`/`toppings` are global, migration-seeded catalogs shared across every restaurant; `pizzas`/`pizza_prices` are restaurant/pizza-scoped. A pizza's topping *selections*, though, aren't a separate aggregate at all — they live on `Pizza` itself (see below). `PizzaResponse` is its own response type, returned by the pizza endpoints above and never nested inside `RestaurantResponse` — the menu is fetched via `GET /:id/pizzas`, not as part of fetching the restaurant.
- **No `DELETE` endpoint for pizzas, by design**: a hard delete would permanently orphan any future order-history reference to that pizza — this monorepo has no order-service yet, but the risk was judged worth designing around now. `Pizza.Status` (`available`/`unavailable`/`archived`, `pizza_status_enum`) is the retirement mechanism instead: `unavailable` is a lighter, reversible pause (e.g. temporarily out of stock), `archived` via `PUT .../pizzaId` is the actual "remove from menu" outcome, and `ListPizzas` filters `archived` out by default. `pizza_prices.pizza_id` is a plain `REFERENCES pizzas (id)` — Postgres default `NO ACTION`, not `ON DELETE CASCADE` — for the same reason: if a `pizzas` row were ever removed by some other path (there is none today), the DB refuses to silently cascade away price history rather than deleting it along with the pizza. `restaurants.id → pizzas.restaurant_id` keeps `ON DELETE CASCADE` — a different relationship, not in scope of this concern.
- **`Pizza.Toppings` is a JSONB array of topping IDs on the `pizzas` row, not a join table — this was a deliberate mid-implementation redesign**: an earlier version of this feature had a `pizza_topping_items` join table (`pizza_id`, `topping_id`, `is_default`) with its own repository, mirroring `pizza_prices`. It was replaced with `pizzas.toppings JSONB NOT NULL DEFAULT '[]'` (just `["<uuid>", ...]`, no `is_default` — that distinction was dropped entirely, not preserved elsewhere) plus two domain methods on `Pizza` (`internal/domain/restaurant/pizza.go`): `ToppingIDs() ([]uuid.UUID, error)` (unmarshal) and `SetToppingIDs([]uuid.UUID) error` (marshal). **Trade-off accepted knowingly**: this drops DB-level referential integrity (no FK from a JSONB array element to `toppings.id`) and the `UNIQUE(pizza_id, topping_id)` constraint the join table had — nothing backstops any of this at the DB layer anymore. What replaces it is split across two layers, deliberately, not lumped into one helper: **existence-in-catalog** is an application-layer check (`ValidateToppingSelections`, `internal/application/restaurant/topping_selection.go`) because it needs data pulled from `ToppingRepository.List` that domain objects in this codebase never hold references to — it's exported and lives in the parent `internal/application/restaurant/` package rather than inside `commands/`, the same place `mapper.go`/`schema.go` already sit, since it isn't itself a use case (no `Execute` method) and is shared plumbing `CreatePizza`/`UpdatePizza` both call into. **No-duplicates**, though, needs no repository data — it's a `Pizza` aggregate invariant, so it lives on `Pizza.SetToppingIDs` itself (`internal/domain/restaurant/pizza.go`): it rejects a repeated ID with the bare domain sentinel `restaurant.ErrDuplicateTopping` (`errors.go`), no `apperr` import, matching how domain errors are written everywhere else in this service. Callers (`CreatePizza`, `UpdatePizza`) then double-wrap it on the way out — `fmt.Errorf("%w: %w", err, apperr.ErrConflict)` — the same multi-`%w` pattern `ErrChecklistIncomplete` already uses, so command-level tests can still assert on `apperr.ErrConflict` directly without `response.HandleError` needing a new case. Reading toppings back (`mapper.ToPizzaResponse`) calls `pizza.ToppingIDs()` and looks each ID up in a `toppings` map (for name) and, where available, a `topping_prices` map (for `ExtraPrice`) built from separate repo calls. `ToppingResponse.ExtraPrice` is `*decimal.Decimal` with `json:"extraPrice,omitempty"`, not a bare `decimal.Decimal` — a `0` would falsely read as "free," when the real meaning of an unset price is "this restaurant hasn't priced this topping as an add-on," so `mapper.ToPizzaResponse` only sets the pointer when `priceByToppingID` actually has an entry (`if price, ok := priceByToppingID[toppingID]; ok { extraPrice = &price }`), leaving it `nil` (omitted from the JSON) otherwise. `CreatePizza`/`UpdatePizza` deliberately pass a `nil` price map, though — a default topping is already priced into the pizza itself, so showing *any* extra price for it made no sense once pricing stopped gating whether a topping could be a default (see below); their responses always omit `extraPrice` entirely for every topping. Only `ListPizzas` (`GET /:id/pizzas`, menu display) still fetches `topping_prices` and populates it for real — `CreatePizza`/`UpdatePizza` no longer take a `ToppingPriceRepository` dependency at all.
- **There is no dedicated `PUT .../toppings` endpoint — it existed briefly, then was removed**: a pizza's default toppings are set entirely through `CreatePizza`/`UpdatePizza`'s `toppingIds` field now (see the route bullets above). The standalone `SetPizzaToppings` command, its handler method, its route, and its tests were all deleted once `UpdatePizza` grew the same capability — two ways to do the same thing was judged not worth keeping. If you're looking for "how does an existing pizza's topping list get replaced," the answer is `PUT /:id/pizzas/:pizzaId` with a `toppingIds` key present in the body, not a separate sub-resource call.
- **`SetPizzaPrices` toggles, sizes previously priced but omitted from a request become inactive rather than deleted**: `PizzaPriceRepository.ReplacePrices` upserts (`ON CONFLICT (pizza_id, size_id) DO UPDATE` sets `price`/`is_active`/`updated_at`) then deactivates (`is_active = false`) any existing row whose `size_id` wasn't in the request — chosen so temporarily disabling a size doesn't lose its price. This is the one remaining use of `ReplacePrices`'s naming/behavior history (it and `pizza_topping_items`'s now-removed `ReplaceToppingItems` were originally both named `ReplaceForPizza` before being renamed apart) — `ReplacePrices` is still a real DB transaction; setting a pizza's toppings isn't, since it's just a plain `Pizza.Toppings` field update via `pizzaRepo.Update`.
- **Every pizza-mutating response reports the pizza's real, full current state (prices + toppings), never a facet this call happened not to touch — a real bug fix, not the original behavior**: `SetPizzaPrices` used to unconditionally return `toppings: []` (never fetched them, regardless of whether the pizza actually had any), and `UpdatePizza` used to return `prices: []` unconditionally and `toppings: []` whenever a request omitted `toppingIds` — both looked identical to "this pizza genuinely has none," which was false the moment the pizza already had prices/toppings from an earlier call. `CreatePizza` never had this problem and needed no fix — a brand-new pizza genuinely has no prices, and no toppings unless set in that same call, so an empty response there is always true. `UpdatePizza` and `SetPizzaPrices` (`internal/application/restaurant/commands/update_pizza.go`/`set_pizza_prices.go`) now both unconditionally fetch `pizza.ToppingIDs()` + `ToppingRepository.List()` for the toppings side and `PizzaPriceRepository.ListByPizza`/`PizzaSizeRepository.List` for the prices side, after applying whatever that call's own change was — regardless of which facet was actually just mutated. Both still pass a `nil` price map into `mapper.ToPizzaResponse` (see the `ExtraPrice` bullet above) — reporting the *real* topping list is a different concern from showing *extra-topping pricing* on it, and the latter still only happens in `ListPizzas`.
- **`topping_prices` and a pizza's default toppings (`Pizza.Toppings`) are unrelated concerns — this was a real design correction, not always the model**: an earlier version of this feature required a topping to already have a `topping_prices` row before it could be set as one of a pizza's defaults (`SetPizzaToppings`/`ValidateToppingSelections` used to check `priceByToppingID` too, and `CreatePizza`/`UpdatePizza` rejected an unpriced topping with `409 Conflict`). That was wrong: a pizza's default toppings are already priced into the pizza's own price (like mozzarella isn't a line item on a Margherita), whereas `topping_prices` is what a restaurant charges for a topping a *customer* adds at order time — a different flow entirely, relevant to a future ordering feature, not to menu authoring. `ValidateToppingSelections` was corrected to check only `toppingByID` (catalog existence), dropping the `priceByToppingID`/`decimal` parameter entirely — see the domain-boundary bullet above for what's left of it. `toppings` (renamed from `pizza_toppings` — the `pizza_` prefix was dropped for consistency with `topping_prices`, which was never prefixed; the Go type followed too, `PizzaTopping` → `Topping`, `PizzaToppingRepository` → `ToppingRepository`, files `pizza_topping.go`/`pizza_topping_repository.go` → `topping.go`/`topping_repository.go`) remains a marketplace-wide catalog — `name`, `description`, `is_vegetarian` — with no price and no availability flag of its own; an even earlier version had `extra_price`/`is_available` columns directly on `toppings` itself, which was wrong for a different reason (every restaurant would've charged the same amount for "Extra Cheese") and was corrected before that — not to be confused with `topping_prices.extra_price` below, a same-named column on a different table for a different, still-valid reason. `topping_prices` (`internal/domain/restaurant/topping_price.go`, `ToppingPriceRepository`, `internal/infrastructure/persistence/topping_price_repository.go`) holds `(restaurant_id, topping_id) → extra_price` (Go field `ExtraPrice`, JSON `extraPrice` on both `ToppingPriceInput`/`ToppingPriceResponse` and the topping entries embedded in `PizzaResponse.Toppings`) — purely a restaurant's own extra-topping price list now, no longer a gate on anything about a pizza's defaults. `ToppingPriceRepository.UpsertPrices` is deliberately upsert-only (unlike `ReplacePrices`'s upsert-and-deactivate) — see the `PUT /:id/topping-prices` route bullet above for why there's no un-pricing path yet.
- **`extra_price` range validation is deliberately split between application and DB layers, with different bounds on purpose**: `SetToppingPrices` (`internal/application/restaurant/commands/set_topping_prices.go`) rejects any `extraPrice` outside `[1, 3]` (`minToppingExtraPrice`/`maxToppingExtraPrice`, `decimal.NewFromInt`) before it ever reaches the repository, wrapping with a new sentinel `apperr.ErrInvalid` (`internal/shared/errors/errors.go`) — mapped to `422 Unprocessable Entity` in `response.HandleError`, the same status Gin's own binding-validation failures return, so an out-of-range business value and a malformed request body look the same to the client. The migration's own `CHECK` constraint (`007_create_topping_prices.up.sql`) is deliberately looser — `extra_price >= 1` only, no upper bound — a floor, not the real business rule: the DB is a backstop against garbage bypassing the application layer entirely (a future direct-SQL path, a bug in a different command), not the source of truth for "what's the max a restaurant can charge for extra cheese," which is a product decision that can change without a migration. This is the same backstop-not-primary-validation split already established for duplicate-ID checks elsewhere in this file (Go rejects first, the DB `UNIQUE`/`CHECK` constraint is what stops anything that slips past). `go-playground/validator`'s numeric tags can't do this directly (see the `decimal.Decimal` validator-tag bullet below) — this had to be hand-rolled in the command, not a binding tag on `ToppingPriceInput.ExtraPrice`.
- **Payout details are versioned, not overwritten in place**: `payout_details` (`internal/domain/restaurant/payout_details.go`, Go type `PayoutDetails`) is a separate table with its own surrogate `id` PK (not `restaurant_id` — this table intentionally holds multiple historical rows per restaurant, one per submission). Each row has a `status`: `pending` (awaiting verification — every submission lands here, including the first), `active` (currently receiving payouts), or `superseded` (a former `pending`/`active` row that's been replaced). Two partial unique indexes (`uq_payout_details_restaurant_active`, `uq_payout_details_restaurant_pending`, same technique as `restaurants.slug`) enforce at most one `active` and at most one `pending` row per restaurant **at the DB level**. `PayoutDetailsRepository.Create` (`internal/infrastructure/persistence/payout_details_repository.go`) is a plain insert — it deliberately does *not* supersede an existing pending row; if one exists, the partial unique index raises a Postgres `23505` unique-violation, which `Create` translates into `restaurant.ErrPendingPayoutExists` — the persistence layer returns the sentinel only, and `response.HandleError` (`internal/interfaces/http/response/error_response.go`) owns the `409` status and user-facing message, keeping request/response wording out of the persistence layer. `PayoutDetailsRepository.UpdatePending` edits a `pending` row in place via a single `UPDATE ... WHERE restaurant_id = ? AND status = 'pending'` — atomic rather than read-then-write, so a concurrent review-promotion flipping the row to `active` mid-edit just causes the edit to affect zero rows (translated to `restaurant.ErrNoPendingPayout`) instead of corrupting an already-approved record. Editing a `pending` row in place is safe specifically because it hasn't been reviewed yet — there's no history to lose, unlike `active`/`superseded` rows, which no code path ever mutates. An existing `active` row is never touched by `Create` or `UpdatePending` regardless — only a future review-promotion step changes it. **There is no promotion path (`pending`→`active`) implemented yet** — same "schema ahead of the code" gap as `Checklist.IsCompleted()` never being checked and `restaurants.status` never transitioning past `review`; a future admin/review process is expected to handle both together. It's still part of the `Restaurant` aggregate, not a separate one: `Restaurant.PayoutDetails *PayoutDetails` is a GORM has-one association, and `RestaurantRepository.FindByIDAndOwner` `Preload`s only the `active` row (so `RestaurantResponse.Payout` reflects what's actually being paid out, not a stale/pending submission) — the `CreatePayout` command overrides this in its own response to show what was just submitted instead. `RestaurantRepository.Update` uses `.Omit(clause.Associations)` so saving the restaurant row never implicitly cascades into `payout_details` — all writes to that table go through `PayoutDetailsRepository.Create` only.
- **`iban`/`bic`/`hhmm` are custom-registered validator tags, not all go-playground built-ins**: `go-playground/validator/v10` (this repo's version) has no built-in `iban` tag — `internal/interfaces/http/validation/validators.go` registers one via `init()` (ISO 13616 mod-97 checksum) on Gin's shared validator engine. `bic` *is* a real built-in tag (ISO 9362 format) — don't confuse it with the non-existent `bic_swift`. `hhmm` is also custom (regex `HH:MM`, `00`-`23`:`00`-`59`), used by `DayRangeRequest.Open`/`Close`. The `Open < Close` ordering check for opening-hours ranges is a struct-level validation (`engine.RegisterStructValidation(validateDayRange, restaurant.DayRangeRequest{})`, note: `restaurant` here is `internal/application/restaurant`, not the domain package) rather than a field tag, since go-playground's `gtfield`/`ltfield` compare string *length* for `Kind` `String`, not lexical value — cross-field comparisons on strings need a custom struct-level function instead.
- **Geocoding is conditional**: `internal/application/restaurant/commands/update_address.go` only calls `geocoder.GeocodeAddress` (OpenCage, `internal/infrastructure/geocoder/opencage.go`, 5s HTTP timeout) when the incoming `Address` struct differs from the stored one — otherwise it reuses the existing `Lat`/`Lon`. Preserve this comparison if touching address-update logic; it's a deliberate perf/cost optimization (avoids unnecessary paid API calls), not an oversight.
- **Slug generation**: `UpdateAddress.generateUniqueSlug` builds a slug from name+city+street and probes `-2` through `-9` suffixes for collisions, giving up after 9 attempts. It's called on every address update (not just creation), so a restaurant's slug can change when its address changes.
- **Auth model differs from identity-service**: this service does **not** parse JWTs itself. `internal/interfaces/http/middleware/auth_middleware.go` only reads `X-User-ID`/`X-User-Role` headers (injected by Traefik after identity-service's forward-auth check) and 401s if missing — see root `CLAUDE.md`. `RequireRole`/`EnsureOwner` then gate by role. Note: `JWT_SECRET` is present in `.env.example` but is not read by any current middleware here — treat it as unused/vestigial rather than load-bearing.
- **`decimal.Decimal` request fields can't carry numeric validator tags**: `go-playground/validator/v10`'s numeric tags (`gte`, `lte`, `min`, `max`, ...) panic on `shopspring/decimal.Decimal` fields (`Bad field type decimal.Decimal`) — it isn't a `Kind` the validator understands. `UpdateDeliveryRequest.DeliveryFee`/`MinimumOrder` (`internal/application/restaurant/schema.go`) therefore carry no validation tag; the DB's `CHECK (... >= 0)` constraints are the only guard. Follow the same tag-less pattern for any new `decimal.Decimal` request field.
- **`Money` (`internal/application/restaurant/money.go`) exists specifically to stop trailing zeros disappearing in JSON responses — a real, confirmed bug, not a style preference**: `decimal.Decimal`'s `MarshalJSON()` calls `String()`, which (verified against `shopspring/decimal@v1.4.0` source, `d.string(true)`) *deliberately* trims trailing zeros from the fractional part — a price stored and read back correctly as `1.50` (confirmed via `NUMERIC(6,2)`'s own `::text` cast and the Go value's internal `exp:-2`, both correct) still rendered as `"1.5"` in the response, `1.00` as `"1"`. This is why every `decimal.Decimal.Equal(...)` assertion in this codebase's tests never caught it — `Equal` compares numeric value, not string form, and `1.5 == 1.50` numerically. `Money` is `type Money decimal.Decimal` with `MarshalJSON`/`UnmarshalJSON` implemented via `StringFixed(2)` instead of `String()`, always emitting exactly 2 decimal places. **Scope**: every response money field now uses `Money` — `PizzaPriceResponse.Price`, `ToppingResponse.ExtraPrice` (`*Money`), `ToppingPriceResponse.ExtraPrice`, and `DeliveryResponse.Fee`/`MinimumOrder` (the last two converted in a follow-up fix after initially being left as plain `decimal.Decimal`, since they had the exact same latent bug). Request/input fields (`PizzaPriceInput.Price`, `ToppingPriceInput.ExtraPrice`, `UpdateDeliveryRequest.DeliveryFee`/`MinimumOrder`) stay plain `decimal.Decimal` — display formatting is a response-only concern, inputs just need the numeric value. `mapper.go` wraps at construction time (`Money(p.Price)`, `Money(price.ExtraPrice)`, or `&Money(...)` via a local var for the pointer case since Go won't let you `&Money(x)` directly) — the domain layer (`Pizza`, `PizzaPrice`, `ToppingPrice`) keeps plain `decimal.Decimal` throughout; `Money` is purely an application/response-layer concern, never a domain or persistence type.
- **Error convention**: same shared-sentinel pattern as identity-service — `internal/shared/errors/errors.go` (`ErrForbidden`, `ErrNotFound`, `ErrConflict`, `ErrInvalid`, etc.) plus domain-specific errors in `internal/domain/restaurant/errors.go` (`ErrEmailAlreadyExists`, `ErrPendingPayoutExists`, `ErrNoPendingPayout`, `ErrDuplicateTopping`). Repository/persistence code returns these bare, with no embedded user-facing text; `response.HandleError` (`internal/interfaces/http/response/error_response.go`) owns the HTTP status and message for each. `ErrInvalid` (→ `422`) is the newest addition — for business-rule input validation that can't be expressed as a Gin binding tag (e.g. `SetToppingPrices`'s `extraPrice` range, since `decimal.Decimal` can't carry numeric tags at all, see below) but should still read to the client like the tag-based validation failures do. Follow this same split for any new domain error.
- **Observability**: `internal/infrastructure/observability/` provides a Gin middleware that injects a per-request `slog.Logger` (with a generated request ID) into context, retrieved via `logger.FromContext`/`logger.WithContext`. Use this instead of a package-level logger when adding logging in request-scoped code.

## Testing conventions

Same shape as identity-service: `tests/` mirrors `internal/`, `tests/testutil/db.go` gives a real GORM `TestDB` + table truncation, `tests/infrastructure/db/fixtures/*.go` provide `LoadXFixtures(t, db)` helpers (`restaurant_fixture.go` includes restaurants with varying checklist completeness — check there before writing new ones covering onboarding states; `pizza_fixture.go` seeds two pizzas onto the "Anatolische Küche" fixture restaurant, the only one with a completed checklist).

**Truncating just `restaurants` is enough, even for pizza-related tests**: `TestDB.TruncateTables` uses `TRUNCATE ... CASCADE`, which cascades along FK edges regardless of each FK's own `ON DELETE` setting (a different mechanism from `ON DELETE CASCADE`, which only governs plain `DELETE` statements) — so `db.TruncateTables(t, testutil.TableRestaurant)` alone also clears `pizzas`/`pizza_prices`/`topping_prices`, the same way it already clears `payout_details`. A pizza's toppings live inside the `pizzas` row itself (`toppings` JSONB column) so there's nothing extra to truncate for those. There is no `TablePizza`/`TablePizzaPrice`/`TableToppingPrice` constant in `testutil/db.go` and there shouldn't be one — checked precedent: `payout_details` (also FK-cascading from `restaurants`) has no dedicated constant either. `pizza_sizes`/`toppings` are global catalogs seeded once by migrations and never truncated between tests (same as the existing, unused `TablePizzaSize` constant) — don't add truncation for them.
