# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Scope: this file covers `restaurant-service` only. See the root `CLAUDE.md` for monorepo-wide architecture and how this service fits into the event flow.

## What this service owns

Restaurant records and their onboarding checklist. It is the only service that talks to `postgres-restaurant` and the OpenCage geocoding API. It does **not** implement the outbox pattern (see root `CLAUDE.md`) — its `cmd/worker` is a plain RabbitMQ *consumer*, not an outbox relay.

Routes (behind Traefik, JWT-protected + owner-only):
- `PATCH /restaurants/:id/address` — updates address, re-geocoding only if it changed (`internal/interfaces/http/handlers/address_handler.go`).
- `PATCH /restaurants/:id/delivery` — updates pickup/delivery-type/radius/fee/minimum-order (`internal/interfaces/http/handlers/delivery_handler.go`).
- `POST /restaurants/:id/payout-details` — submits payout bank details (account holder, IBAN, BIC, bank name) as a new `pending` record awaiting verification, returns `201 Created`; `409 Conflict` if a `pending` record already exists (`internal/interfaces/http/handlers/payout_handler.go`, method `CreatePayout`). `POST`, not `PUT`/`PATCH`: every successful call inserts a brand-new row rather than converging to a fixed state, so this isn't idempotent and doesn't fit PUT's create-or-replace-at-known-URI contract — it's a "submit for review" action, not a resource replacement. Note the route says `payout` while the checklist item it completes is `ChecklistPayment` (`"payment"`) — that's deliberate, not a typo: the checklist step name predates this feature and represents the onboarding step ("have they set up payment"), while `payout` is the more precise term for what's actually stored (the restaurant's payout destination, as opposed to how a customer pays).
- `PUT /restaurants/:id/payout-details` — replaces the `pending` submission's fields in place (method `UpdatePayout`), full replace (all four fields required). Deliberately `PUT`, not `PATCH` like `address`/`delivery` — even though those two are also full-replace, this one is conditional on a `pending` record existing rather than an unconditional "resource at this URI is now exactly this," so it's called out with a different verb rather than following those two by default. `404 Not Found` (`restaurant.ErrNoPendingPayout`) if there is no `pending` record — including when only an `active` record exists. Unlike every other mutating command in this file, `UpdatePayout` does **not** call `restaurantRepo.Update`: `ChecklistPayment` is already true from `Create`, and no `restaurants` column changes, so touching that table here would just be a spurious `UpdatedAt` bump. There is still no way to cancel/withdraw a `pending` submission — that was deliberately removed (see git history around 2026-08-04) in favor of this edit endpoint and hasn't been reintroduced.
- `PATCH /restaurants/:id/opening-hours` — replaces the weekly schedule (method `UpdateOpeningHours`), full replace like `address`/`delivery`. Each weekday (`Monday`...`Sunday`) holds a list of `internal/domain/restaurant.DayRange{Open, Close string}` in `HH:MM`; an empty/nil list means closed that day. Multiple ranges per day are supported (e.g. lunch/dinner split). Ranges are calendar-day-bound — `Close` must be later than `Open`, no crossing midnight within one range — so a place open past midnight represents that as two entries (e.g. `monday: 15:00-23:59` plus `tuesday: 00:00-03:00` for the carryover) rather than one range spanning two days.

## Commands

Run from inside `restaurant-service/`:
```bash
go run ./cmd/api      # HTTP API (or `air -c .air.toml` for live reload, matches the dev container)
go run ./cmd/worker   # RabbitMQ consumer for identity events — NOT started by compose.yaml, run manually
go test ./...
go test ./... -run TestName
```
Tests are integration-style against real Postgres (see root `CLAUDE.md` for `compose.test.yaml`); no mocked-DB path. Needs `.env.test` populated like `.env.example` (including `OPENCAGE_API_KEY`).

Migrations (`internal/infrastructure/migrations/*.sql`, golang-migrate) define `restaurants`, `pizza_sizes`, and `payout_details`. Note `pizza_sizes` has a Go model (`internal/domain/restaurant/pizza_size.go`) and a test fixture but **no repository or application code uses it yet** — schema is ahead of the code.

## Architecture specifics

- **`cmd/worker` here is the `restaurant-worker` from the root architecture diagram**: it consumes `restaurant.initiated` off RabbitMQ (published by `identity-service`'s outbox) and creates the local `Restaurant` row. Wiring: `internal/container/worker.go` registers `events.RestaurantInitiated` against routing key `restaurant.initiated` on an in-process `EventDispatcher` (`internal/application/restaurant/events/dispatcher.go`); `internal/infrastructure/messaging/rabbitmq_consumer.go` pulls messages and calls `dispatcher.Dispatch`. To handle a new inbound event type, add a handler implementing `restaurant.EventHandler` and register it in `container/worker.go` plus add its routing key to `messaging.Exchanges["identity.events"]`.
- **Consumer reliability**: manual ack, QoS prefetch 1, a dead-letter exchange (`restaurant_dlx`) wired to the main queue, and in-process retry via `x-retry-count` header (linear backoff, `MaxRetryAttempts = 3` before the message is discarded). This is a different reliability mechanism from identity-service's outbox — don't conflate the two when reasoning about delivery guarantees.
- **Restaurant onboarding is checklist-driven**: `internal/domain/restaurant/checklist.go` defines six required items (`basic`, `contract`, `address`, `delivery`, `payment`, and `ChecklistOpeningHours` — value `"openinghours"`, matching the other five items' single-word-no-separator convention) and `Checklist.IsCompleted()`. `RestaurantInitiated` (the `restaurant.initiated` handler) marks `basic` complete on creation; `UpdateAddress` marks `address` complete; `UpdateDelivery` marks `delivery` complete; `CreatePayout` marks `payment` complete; `UpdateOpeningHours` marks `ChecklistOpeningHours` complete. Only `contract` has no endpoint/handler yet, so `IsCompleted()` can never return true until that's implemented. **No code currently checks `IsCompleted()` or transitions `Status` to `active`/publishes `restaurant.launched`** — the launch flow described in the root README/architecture doc is not yet implemented here. If asked to implement `contract`, follow the `UpdateAddress`/`UpdateDelivery`/`CreatePayout`/`UpdateOpeningHours` pattern (ownership check → mark checklist item → mutate → persist → map response).
- **Payout details are versioned, not overwritten in place**: `payout_details` (`internal/domain/restaurant/payout_details.go`, Go type `PayoutDetails`) is a separate table with its own surrogate `id` PK (not `restaurant_id` — this table intentionally holds multiple historical rows per restaurant, one per submission). Each row has a `status`: `pending` (awaiting verification — every submission lands here, including the first), `active` (currently receiving payouts), or `superseded` (a former `pending`/`active` row that's been replaced). Two partial unique indexes (`uq_payout_details_restaurant_active`, `uq_payout_details_restaurant_pending`, same technique as `restaurants.slug`) enforce at most one `active` and at most one `pending` row per restaurant **at the DB level**. `PayoutDetailsRepository.Create` (`internal/infrastructure/persistence/payout_details_repository.go`) is a plain insert — it deliberately does *not* supersede an existing pending row; if one exists, the partial unique index raises a Postgres `23505` unique-violation, which `Create` translates into `restaurant.ErrPendingPayoutExists` — the persistence layer returns the sentinel only, and `response.HandleError` (`internal/interfaces/http/response/error_response.go`) owns the `409` status and user-facing message, keeping request/response wording out of the persistence layer. `PayoutDetailsRepository.UpdatePending` edits a `pending` row in place via a single `UPDATE ... WHERE restaurant_id = ? AND status = 'pending'` — atomic rather than read-then-write, so a concurrent review-promotion flipping the row to `active` mid-edit just causes the edit to affect zero rows (translated to `restaurant.ErrNoPendingPayout`) instead of corrupting an already-approved record. Editing a `pending` row in place is safe specifically because it hasn't been reviewed yet — there's no history to lose, unlike `active`/`superseded` rows, which no code path ever mutates. An existing `active` row is never touched by `Create` or `UpdatePending` regardless — only a future review-promotion step changes it. **There is no promotion path (`pending`→`active`) implemented yet** — same "schema ahead of the code" gap as `Checklist.IsCompleted()` never being checked and `restaurants.status` never transitioning past `review`; a future admin/review process is expected to handle both together. It's still part of the `Restaurant` aggregate, not a separate one: `Restaurant.PayoutDetails *PayoutDetails` is a GORM has-one association, and `RestaurantRepository.FindByIDAndOwner` `Preload`s only the `active` row (so `RestaurantResponse.Payout` reflects what's actually being paid out, not a stale/pending submission) — the `CreatePayout` command overrides this in its own response to show what was just submitted instead. `RestaurantRepository.Update` uses `.Omit(clause.Associations)` so saving the restaurant row never implicitly cascades into `payout_details` — all writes to that table go through `PayoutDetailsRepository.Create` only.
- **`iban`/`bic`/`hhmm` are custom-registered validator tags, not all go-playground built-ins**: `go-playground/validator/v10` (this repo's version) has no built-in `iban` tag — `internal/interfaces/http/validation/validators.go` registers one via `init()` (ISO 13616 mod-97 checksum) on Gin's shared validator engine. `bic` *is* a real built-in tag (ISO 9362 format) — don't confuse it with the non-existent `bic_swift`. `hhmm` is also custom (regex `HH:MM`, `00`-`23`:`00`-`59`), used by `DayRangeRequest.Open`/`Close`. The `Open < Close` ordering check for opening-hours ranges is a struct-level validation (`engine.RegisterStructValidation(validateDayRange, restaurant.DayRangeRequest{})`, note: `restaurant` here is `internal/application/restaurant`, not the domain package) rather than a field tag, since go-playground's `gtfield`/`ltfield` compare string *length* for `Kind` `String`, not lexical value — cross-field comparisons on strings need a custom struct-level function instead.
- **Geocoding is conditional**: `internal/application/restaurant/commands/update_address.go` only calls `geocoder.GeocodeAddress` (OpenCage, `internal/infrastructure/geocoder/opencage.go`, 5s HTTP timeout) when the incoming `Address` struct differs from the stored one — otherwise it reuses the existing `Lat`/`Lon`. Preserve this comparison if touching address-update logic; it's a deliberate perf/cost optimization (avoids unnecessary paid API calls), not an oversight.
- **Slug generation**: `UpdateAddress.generateUniqueSlug` builds a slug from name+city+street and probes `-2` through `-9` suffixes for collisions, giving up after 9 attempts. It's called on every address update (not just creation), so a restaurant's slug can change when its address changes.
- **Auth model differs from identity-service**: this service does **not** parse JWTs itself. `internal/interfaces/http/middleware/auth_middleware.go` only reads `X-User-ID`/`X-User-Role` headers (injected by Traefik after identity-service's forward-auth check) and 401s if missing — see root `CLAUDE.md`. `RequireRole`/`EnsureOwner` then gate by role. Note: `JWT_SECRET` is present in `.env.example` but is not read by any current middleware here — treat it as unused/vestigial rather than load-bearing.
- **`decimal.Decimal` request fields can't carry numeric validator tags**: `go-playground/validator/v10`'s numeric tags (`gte`, `lte`, `min`, `max`, ...) panic on `shopspring/decimal.Decimal` fields (`Bad field type decimal.Decimal`) — it isn't a `Kind` the validator understands. `UpdateDeliveryRequest.DeliveryFee`/`MinimumOrder` (`internal/application/restaurant/schema.go`) therefore carry no validation tag; the DB's `CHECK (... >= 0)` constraints are the only guard. Follow the same tag-less pattern for any new `decimal.Decimal` request field.
- **Error convention**: same shared-sentinel pattern as identity-service — `internal/shared/errors/errors.go` (`ErrForbidden`, etc.) plus domain-specific errors in `internal/domain/restaurant/errors.go` (`ErrEmailAlreadyExists`, `ErrPendingPayoutExists`, `ErrNoPendingPayout`). Repository/persistence code returns these bare, with no embedded user-facing text; `response.HandleError` (`internal/interfaces/http/response/error_response.go`) owns the HTTP status and message for each. Follow this same split for any new domain error.
- **Observability**: `internal/infrastructure/observability/` provides a Gin middleware that injects a per-request `slog.Logger` (with a generated request ID) into context, retrieved via `logger.FromContext`/`logger.WithContext`. Use this instead of a package-level logger when adding logging in request-scoped code.

## Testing conventions

Same shape as identity-service: `tests/` mirrors `internal/`, `tests/testutil/db.go` gives a real GORM `TestDB` + table truncation, `tests/infrastructure/db/fixtures/*.go` provide `LoadXFixtures(t, db)` helpers (`restaurant_fixture.go` includes restaurants with varying checklist completeness — check there before writing new ones covering onboarding states).
