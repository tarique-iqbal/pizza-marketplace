# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Scope: this file covers `restaurant-service` only. See the root `CLAUDE.md` for monorepo-wide architecture and how this service fits into the event flow.

## What this service owns

Restaurant records and their onboarding checklist. It is the only service that talks to `postgres-restaurant` and the OpenCage geocoding API. It implements the transactional outbox pattern (see root `CLAUDE.md`) for **every** event it raises — its `cmd/worker` runs two goroutines: the inbound `restaurant.initiated` consumer, and an outbox relay. There is no best-effort/direct-publish path anywhere in this service.

Routes (behind Traefik, JWT-protected + owner-only):
- `PATCH /restaurants/:id/contact` — updates email/phone/website, full replace (`internal/interfaces/http/handlers/contact_handler.go`). `Email`/`Phone` required, `Website` optional (cleared when omitted). `Phone` uses a custom `phone` validator tag — loose digits/`+`/spaces/hyphens/parens, at least 6 digits, not strict E.164 (real-world input like `+49 40 12345678` isn't E.164-compliant).
- `PATCH /restaurants/:id/address` — updates address, re-geocoding only if it changed (`internal/interfaces/http/handlers/address_handler.go`). Field-level allow-list validation — see the validator-tags bullet below.
- `PATCH /restaurants/:id/delivery` — updates pickup/delivery-type/radius/estimated-delivery-time-range/fee/minimum-order (`internal/interfaces/http/handlers/delivery_handler.go`). `deliveryTimeMin`/`deliveryTimeMax` (minutes, `5`-`120`) follow `deliveryKm`'s own conditional-required rule — both required whenever `deliveryType != "none"`, and validated as a pair (`max > min`, strict) by a struct-level validator (`validateDelivery`). Response mirrors `DisplayAddress`'s precedent: raw `delivery.estimatedMinutesMin`/`Max` plus a computed top-level `estimatedDelivery` string (e.g. `"30-45 min"`, omitted for pickup-only) from `formatDeliveryTime` in `mapper.go` — response-only, never on the wire event payloads.
- `PATCH /restaurants/:id/tags` — replaces dietary/religious tags (`UpdateTags`, `internal/interfaces/http/handlers/tags_handler.go`), full replace. Owner self-declares `vegetarian`/`vegan`/`glutenfree`/`halal` from a fixed enum (`restaurant.RestaurantTag`) — unrelated to `Pizza.IsVegetarian`/`Topping.IsVegetarian`, a separate per-pizza/per-topping concept. No checklist gate, settable at any onboarding stage. Gin-binding validation (`unique,dive,oneof=...`) backstopped by a DB `CHECK` (`ck_restaurants_tags`).
- `POST /restaurants/:id/payout-details` — submits payout bank details as a new `unverified` record, `201`; `409` if an `unverified` record already exists (`internal/interfaces/http/handlers/payout_handler.go`, `CreatePayout`). `POST` not `PUT`/`PATCH`: each call inserts a new row rather than converging to a fixed state — a "submit for review" action, not a resource replacement. Completes checklist item `ChecklistPayout` (`"payout"`).
- `PUT /restaurants/:id/payout-details` — replaces the `unverified` submission's fields in place (`UpdatePayout`), full replace. `PUT`, conditional on an `unverified` record existing — `404` (`payout.ErrNoUnverifiedPayout`) otherwise, including when only an `active` record exists. Doesn't call `restaurantRepo.Update` — `ChecklistPayout` is already true and no `restaurants` column changes.
- `PATCH /restaurants/:id/opening-hours` — replaces the weekly schedule (`UpdateOpeningHours`), full replace. Each weekday holds a list of `internal/domain/restaurant.DayRange{Open, Close string}` in `HH:MM`; empty/nil means closed. Multiple ranges per day supported (lunch/dinner split). Ranges are calendar-day-bound — `Close` must be later than `Open`, no crossing midnight within one range — a place open past midnight uses two entries (e.g. `monday: 15:00-23:59` + `tuesday: 00:00-03:00`).
- `GET /restaurants/:id/pizzas` — lists pizzas (`ListPizzas`). Excludes `status: archived` by default; `available`/`unavailable` both show. No checklist gate. No single-pizza `GET` yet.
- `POST /restaurants/:id/pizzas` — creates a pizza (`CreatePizza`). **Checklist-gated**: `403` (`restaurant.ErrChecklistIncomplete`) unless all six checklist items are complete. Optional `toppingIds` validates existence only (`ValidateToppingSelections`) then calls `pizza.SetToppingIDs(...)` (rejects duplicates) to set default toppings in the same call.
- `PUT /restaurants/:id/pizzas/:pizzaId` — full replace of a pizza's own fields (`name`, `image`, `isVegetarian`, `status`, `sortOrder`, `toppingIds`) (`UpdatePizza`). No checklist gate, no `description`. `isVegetarian`/`status` omitted from the body keep their existing value. `toppingIds` follows the same rule at the slice level: absent (`nil`) leaves toppings untouched entirely; present (even `[]`) means "replace with exactly this." This nil-vs-empty distinction is why `ToppingIDs` stays a plain `[]uuid.UUID`, not a pointer. Response always reports the pizza's real current prices and toppings, regardless of what this call changed.
- `PUT /restaurants/:id/pizzas/:pizzaId/prices` — sets per-size prices (`SetPizzaPrices`). Upsert-and-deactivate: sizes in the request become active at the given price; sizes previously priced but omitted become `isActive: false`, not deleted. Response always reports the pizza's real current toppings too, even though this call never touches them.
- `PUT /restaurants/:id/topping-prices` — sets the restaurant's own price for a customer-requested extra topping (`SetToppingPrices`, `internal/interfaces/http/handlers/topping_price_handler.go`) — unrelated to a pizza's own default toppings. Upsert-only: toppings priced earlier and omitted stay priced; no way to un-price a topping through this endpoint. `extraPrice` must be `1`-`3` inclusive.

## Commands

Run from inside `restaurant-service/`:
```bash
go run ./cmd/api      # HTTP API (or `air -c .air.toml` for live reload, matches the dev container)
go run ./cmd/worker   # RabbitMQ consumer for identity events (or `air -c .air.worker.toml` for live
                       # reload, matches the dev container) — IS started by compose.yaml (restaurant-worker)
go test ./...
go test ./... -run TestName
```
Tests are integration-style against real Postgres (see root `CLAUDE.md` for `compose.test.yaml`); no mocked-DB path. Needs `.env.test` populated like `.env.example` (including `OPENCAGE_API_KEY`).

Migrations (`internal/infrastructure/migrations/*.sql`, golang-migrate) define `restaurants`, `pizza_sizes`, `payout_details`, `pizzas`, `pizza_prices`, `toppings`, and `topping_prices`. No `pizza_topping_items` table — a pizza's topping selections live directly on `pizzas.toppings` (`JSONB NOT NULL DEFAULT '[]'`), a plain array of topping IDs (see below). `pizza_sizes` has a Go model (`internal/domain/restaurant/pizza_size.go`) but no fixture and no repository/application code beyond `PizzaSizeRepository.List` (validates a `SizeID` reference in `SetPizzaPrices`). `toppings` is a global, migration-seeded catalog (12 seed rows) like `pizza_sizes`, with no price of its own — `topping_prices` holds a restaurant's own price for a customer-requested extra topping, a separate concern from a pizza's own defaults.

## Architecture specifics

- **`cmd/worker` is the `restaurant-worker` from the root architecture diagram, running two independent goroutines**: an inbound consumer and an outbox relay, started side by side in `cmd/worker/bootstrap/runner.go`'s `start()` (one `sync.WaitGroup`, per-goroutine panic recovery). The inbound goroutine consumes `restaurant.initiated` (published by identity-service's outbox) and creates the local `Restaurant` row. Wiring: `internal/container/worker.go` registers `events.RestaurantInitiated` against routing key `restaurant.initiated` on an in-process `EventDispatcher`; `internal/infrastructure/messaging/rabbitmq_consumer.go` pulls messages and calls `dispatcher.Dispatch`. A new inbound event type needs a handler implementing `restaurant.EventHandler`, registered in `container/worker.go`, plus its routing key added to `messaging.Exchanges["identity.events"]`.
- **Consumer reliability**: manual ack, QoS prefetch 1, a dead-letter exchange (`restaurant_dlx`) on the main queue, in-process retry via `x-retry-count` (linear backoff, `MaxRetryAttempts = 3` before discard). Separate mechanism from the outbox below — the consumer's reliability is about not losing a message already delivered by RabbitMQ; the outbox is about not losing an event before it reaches RabbitMQ. `ensureConnected` checks both `c.conn.IsClosed()` and `c.channel.IsClosed()` before reconnecting, and `connect()` closes any existing `conn`/`channel` first — a channel can die from an AMQP exception while the connection stays open.
- **The outbox relay goroutine**: `internal/domain/outbox/`, `internal/infrastructure/persistence/outbox.go`, `internal/application/outbox/{worker,relay}.go` mirror identity-service's own outbox shape (`OutboxEvent`/`OutboxStatus`/`Worker`/`WorkerConfig`/`DefaultConfig()`/`Relay`). Every command that raises a domain event calls `resapp.DispatchEventsTx` (`internal/application/restaurant/dispatch.go`) — writes an `outbox_events` row inside the same `db.Transaction` as the business write, for every event (`restaurant.ready_for_review`, `restaurant.approved`, `restaurant.launched`, `restaurant.updated`, `restaurant.pizza_updated`, `restaurant.topping_prices_updated`). `internal/container/worker.go`'s `NewWorkerContainer(logger)` builds the `Relay` (wraps a `RabbitMQPublisher`) and `Worker` (`DefaultConfig()`: 2s poll, batch 50, concurrency 5, 3 retries); `cmd/worker/bootstrap/runner.go` starts `OutboxWorker.Start(ctx)` in its own goroutine. `APIContainer` holds no RabbitMQ publisher at all — only `cmd/worker`'s relay publishes.
- **`Run`/`runOnce` are package-level functions, not methods on `*RabbitMQConsumer`**: they take a `messageSource` interface (`GetMessages`/`Republish`) as a plain parameter, same shape as `io.Copy(dst, src)` — lets `tests/infrastructure/messaging/rabbitmq_consumer_test.go` call `messaging.Run(ctx, fakeSource, dispatcher)` directly with no real broker, without a test-only exported constructor.
- **Restaurant onboarding is checklist-driven**: `internal/domain/restaurant/checklist.go` defines six required items (`basic`, `contact`, `address`, `delivery`, `payout`, `ChecklistOpeningHours`) and `Checklist.IsCompleted()`. `RestaurantInitiated` marks `basic`; `UpdateContact`/`UpdateAddress`/`UpdateDelivery`/`CreatePayout`/`UpdateOpeningHours` each mark their own item. `CreatePizza` is the only code path that calls `IsCompleted()`, gating pizza creation on full onboarding — it doesn't gate the restaurant's own status transitions. `Restaurant.Approve()`/`Launch()` move `restaurants.status` `review`→`approved`→`active`, gated by admin-only `POST /restaurants/:id/approve` and owner-only `POST /restaurants/:id/launch`; `Launch()` publishes `restaurant.launched`. `rejected`/`inactive`/`disabled` have no domain methods or endpoints yet.
- **`internal/application/restaurant/queries/` exists alongside `commands/`**: `ListPizzas` is the only read-only use case, and lives in its own `queries/` package rather than `commands/`. Service-specific choice, not a monorepo convention — identity-service keeps its read-only `find_by_id.go` flat alongside its commands. Future read-only use cases here go in `queries/`; mutations go in `commands/`.
- **Every GORM model uses GORM's own timestamp management**: `CreatedAt`/`UpdatedAt` tagged `gorm:"...;autoCreateTime"`/`gorm:"...;autoUpdateTime;default:null"`, no model has a `WithUpdated()` method. **One exception**: `PizzaPriceRepository.ReplacePrices`'s bulk `ON CONFLICT DO UPDATE` upsert doesn't work with bare `autoUpdateTime` — GORM omits a nil `UpdatedAt` from `VALUES` client-side before the SQL is built, and that omission propagates into `EXCLUDED.updated_at` too, leaving even genuinely-updated rows `NULL`. `ReplacePrices` works around this with a manual `UpdatedAt` assignment before the upsert. Plain `.Update()`/`.Updates()` calls don't have this problem.
- **The pizza menu is a set of separate aggregates, never embedded in `RestaurantResponse`**: `internal/domain/restaurant/pizza.go`, `pizza_price.go`, `pizza_size.go`, `topping.go`/`topping_price.go`, each with its own repository. `pizza_sizes`/`toppings` are global catalogs shared across every restaurant; `pizzas`/`pizza_prices` are restaurant/pizza-scoped. `PizzaResponse` is its own type, returned by the pizza endpoints, never nested inside `RestaurantResponse` — the menu is fetched via `GET /:id/pizzas`.
- **No `DELETE` endpoint for pizzas, by design**: a hard delete would orphan a future order-history reference. `Pizza.Status` (`available`/`unavailable`/`archived`) is the retirement mechanism — `unavailable` is a reversible pause, `archived` via `PUT .../pizzaId` is "remove from menu," `ListPizzas` excludes `archived` by default. `pizza_prices.pizza_id` is `REFERENCES pizzas (id)` with default `NO ACTION`, not `ON DELETE CASCADE` — price history survives even if a `pizzas` row were ever removed by some other path. `restaurants.id → pizzas.restaurant_id` keeps `ON DELETE CASCADE`.
- **`Pizza.Toppings` is a JSONB array of topping IDs on the `pizzas` row, not a join table**: `pizzas.toppings JSONB NOT NULL DEFAULT '[]'` (`["<uuid>", ...]`, no per-topping metadata) plus two domain methods on `Pizza`: `ToppingIDs() ([]uuid.UUID, error)` and `SetToppingIDs([]uuid.UUID) error`. No DB-level referential integrity to `toppings.id`, no DB-level uniqueness — both are enforced in code instead, deliberately split across two layers: **existence-in-catalog** is an application-layer check (`ValidateToppingSelections`, `internal/application/restaurant/topping_selection.go`, needs `ToppingRepository.List` data domain objects don't hold); **no-duplicates** is a `Pizza` aggregate invariant on `SetToppingIDs` itself, rejecting a repeat with the bare domain sentinel `restaurant.ErrDuplicateTopping`. Callers (`CreatePizza`, `UpdatePizza`) wrap it `fmt.Errorf("%w: %w", err, apperr.ErrConflict)` on the way out, so command-level tests can assert on `apperr.ErrConflict` directly. Reading toppings back (`mapper.ToPizzaResponse`) calls `pizza.ToppingIDs()` and looks each ID up in a `toppings` map (name) and, where available, a `topping_prices` map (`ExtraPrice`). `ToppingResponse.ExtraPrice` is `*decimal.Decimal` (`json:"extraPrice,omitempty"`), not bare `decimal.Decimal` — `0` would falsely read as "free" when the real meaning of unset is "not priced as an add-on," so the pointer is only set when `priceByToppingID` has an entry. `CreatePizza`/`UpdatePizza` pass a `nil` price map and always omit `extraPrice` — a default topping is already priced into the pizza itself. Only `ListPizzas` populates it for real.
- **`SetPizzaPrices` upserts and deactivates, never deletes**: `PizzaPriceRepository.ReplacePrices` upserts (`ON CONFLICT (pizza_id, size_id) DO UPDATE` sets `price`/`is_active`/`updated_at`) then sets `is_active = false` on any existing row whose `size_id` wasn't in the request — so temporarily disabling a size doesn't lose its price.
- **Every pizza-mutating response reports the pizza's real, full current state (prices + toppings)**, never just the facet a given call touched: `UpdatePizza` and `SetPizzaPrices` both unconditionally fetch `pizza.ToppingIDs()` + `ToppingRepository.List()` for toppings and `PizzaPriceRepository.ListByPizza`/`PizzaSizeRepository.List` for prices, after applying that call's own change. Both pass a `nil` price map into `mapper.ToPizzaResponse` — reporting the real topping list is separate from showing extra-topping pricing, which only `ListPizzas` does.
- **`topping_prices` and a pizza's default toppings (`Pizza.Toppings`) are unrelated concerns**: a pizza's default toppings are already priced into the pizza's own price (mozzarella isn't a line item on a Margherita); `topping_prices` is what a restaurant charges for a topping a *customer* adds at order time — a different flow, relevant to ordering, not menu authoring. `ValidateToppingSelections` checks only catalog existence (`toppingByID`), never price. `toppings` (`internal/domain/restaurant/topping.go`, `ToppingRepository`) is a marketplace-wide catalog — `name`, `description`, `is_vegetarian` — with no price and no availability flag. `topping_prices` (`internal/domain/restaurant/topping_price.go`, `ToppingPriceRepository`) holds `(restaurant_id, topping_id) → extra_price` (Go field `ExtraPrice`, JSON `extraPrice`), purely a restaurant's own extra-topping price list. `ToppingPriceRepository.UpsertPrices` is upsert-only, unlike `ReplacePrices`'s upsert-and-deactivate — there's no un-pricing path yet.
- **`extra_price` range validation is split between application and DB layers, with different bounds on purpose**: `SetToppingPrices` rejects any `extraPrice` outside `[1, 3]` (`minToppingExtraPrice`/`maxToppingExtraPrice`) before it reaches the repository, wrapping `apperr.ErrInvalid` (→ `422`, same status Gin's own binding failures return). The migration's own `CHECK` (`007_create_topping_prices.up.sql`) is looser — `extra_price >= 1` only, no upper bound — a backstop against garbage bypassing the application layer entirely, not the source of truth for the real business rule (which can change without a migration). `go-playground/validator`'s numeric tags can't do this directly on a `decimal.Decimal` field (see below) — hand-rolled in the command instead.
- **Payout details are versioned, not overwritten in place**: `payout_details` (`internal/domain/payout/payout_details.go`) has its own surrogate `id` PK, not `restaurant_id` — holds multiple historical rows per restaurant, one per submission. `status`: `unverified` (awaiting verification, every submission lands here first), `active` (currently receiving payouts), or `superseded`. Two partial unique indexes (`uq_payout_details_restaurant_active`, `uq_payout_details_restaurant_unverified`) enforce at most one `active` and one `unverified` row per restaurant at the DB level. `PayoutDetailsRepository.Create` is a plain insert that relies on the partial unique index (Postgres `23505` → `payout.ErrUnverifiedPayoutExists`) rather than checking first. `UpdateUnverified` edits an `unverified` row atomically (`UPDATE ... WHERE restaurant_id = ? AND status = 'unverified'`) — a concurrent promotion-to-`active` mid-edit just affects zero rows (`payout.ErrNoUnverifiedPayout`) rather than corrupting an approved record. `PromoteToActive` is the `unverified`→`active` path, called by `ApproveRestaurant` right after `res.Approve()` succeeds; not wrapped in the same DB transaction as the restaurant-status write. `Restaurant.PayoutDetails *PayoutDetails` is a GORM has-one association; `RestaurantRepository.FindByIDAndOwner` `Preload`s only the `active` row. `RestaurantRepository.Update` uses `.Omit(clause.Associations)` so saving the restaurant row never cascades into `payout_details`.
- **`iban`/`bic`/`hhmm`/`houseNumber`/`street`/`city`/`postalCode` are custom-registered validator tags, not all go-playground built-ins**: `go-playground/validator/v10` has no built-in `iban` — `internal/interfaces/http/validation/validators.go` registers one via `init()` (ISO 13616 mod-97 checksum). `bic` *is* built-in (ISO 9362) — not `bic_swift`, which doesn't exist. `hhmm` is custom (regex `HH:MM`, `00`-`23`:`00`-`59`), used by `DayRangeRequest.Open`/`Close`. `UpdateAddressRequest`'s four fields each get their own allow-list pattern, since a house number and a city need different allowed characters: `houseNumber` (`^[\p{L}\p{N} ()/-]+$` — allows a unit/room suffix like `"29 (013)"`), `street` (`^[\p{L}\p{N} .'-]+$`), `city` (`^[\p{L} '.-]+$` — letters only, no digits), `postalCode` (`^[A-Za-z0-9 -]+$` — ASCII-only). The `Open < Close` ordering check for opening-hours ranges is a struct-level validation (`engine.RegisterStructValidation(validateDayRange, restaurant.DayRangeRequest{})`) rather than a field tag — go-playground's `gtfield`/`ltfield` compare string *length* for `Kind` `String`, not lexical value.
- **Geocoding is conditional**: `internal/application/restaurant/commands/update_address.go` only calls `geocoder.GeocodeAddress` (OpenCage, `internal/infrastructure/geocoder/opencage.go`, 5s timeout) when the incoming `Address` differs from the stored one — otherwise reuses the existing `Lat`/`Lon`. Preserve this comparison if touching address-update logic.
- **Slug generation**: `UpdateAddress.generateUniqueSlug` builds a slug from name+city+street, probing `-2` through `-9` suffixes for collisions before giving up. Runs on every address update, not just creation — a restaurant's slug can change when its address changes.
- **Auth model differs from identity-service**: doesn't parse JWTs itself. `internal/interfaces/http/middleware/auth_middleware.go` only reads `X-User-ID`/`X-User-Role` headers (injected by Traefik after identity-service's forward-auth check), `401`s if missing. `RequireRole`/`EnsureOwner` gate by role. `JWT_SECRET` in `.env.example` is unused/vestigial, not read by any middleware here.
- **`decimal.Decimal` request fields can't carry numeric validator tags**: `go-playground/validator/v10`'s numeric tags (`gte`, `lte`, `min`, `max`, ...) panic on `shopspring/decimal.Decimal` (`Bad field type decimal.Decimal`). `UpdateDeliveryRequest.DeliveryFee`/`MinimumOrder` carry no validation tag — the DB's `CHECK (... >= 0)` is the only guard. Follow the same tag-less pattern for any new `decimal.Decimal` request field.
- **`Money` (`internal/application/restaurant/money.go`) exists because `decimal.Decimal.MarshalJSON()` trims trailing zeros** (`1.50` → `"1.5"`, `1.00` → `"1"`). `Money` is `type Money decimal.Decimal` with `MarshalJSON`/`UnmarshalJSON` via `StringFixed(2)`, always exactly 2 decimal places. Every response money field uses it: `PizzaPriceResponse.Price`, `ToppingResponse.ExtraPrice` (`*Money`), `ToppingPriceResponse.ExtraPrice`, `DeliveryResponse.Fee`/`MinimumOrder`. Request/input fields stay plain `decimal.Decimal` — display formatting is response-only. `mapper.go` wraps at construction time (`Money(p.Price)`, or `&Money(...)` via a local var for the pointer case, since Go won't let you `&Money(x)` directly). The domain layer (`Pizza`, `PizzaPrice`, `ToppingPrice`) keeps plain `decimal.Decimal` throughout — `Money` is purely an application/response-layer concern.
- **Error convention**: shared-sentinel pattern like identity-service — `internal/shared/errors/errors.go` (`ErrForbidden`, `ErrNotFound`, `ErrConflict`, `ErrInvalid`, etc.) plus domain-specific errors in `internal/domain/restaurant/errors.go` and `internal/domain/payout/errors.go`. Repository/persistence code returns these bare, no embedded user-facing text; `response.HandleError` owns the HTTP status and message for each. `ErrInvalid` (→ `422`) is for business-rule validation that can't be a Gin binding tag (e.g. `SetToppingPrices`'s `extraPrice` range) but should still read like a tag-based failure to the client.
- **Observability**: `internal/infrastructure/observability/` provides a Gin middleware injecting a per-request `slog.Logger` (with a generated request ID) into context, via `logger.FromContext`/`logger.WithContext`. Use this instead of a package-level logger in request-scoped code.

## Testing conventions

Same shape as identity-service: `tests/` mirrors `internal/`, `tests/testutil/db.go` gives a real GORM `TestDB` + table truncation, `tests/infrastructure/db/fixtures/*.go` provide `LoadXFixtures(t, db)` helpers (`restaurant_fixture.go` includes restaurants with varying checklist completeness; `pizza_fixture.go` seeds two pizzas onto the "Anatolische Küche" fixture restaurant, the only one with a completed checklist).

`tests/infrastructure/messaging/rabbitmq_consumer_test.go` needs no DB/fixtures — pure unit tests against `messaging.Run` directly. Needs two local fakes beyond a `mockDispatcher`: a `fakeSource` (`messageSource`'s `GetMessages`/`Republish`, backed by a `chan amqp091.Delivery` plus a slice recording `Republish` calls) and a `fakeAcknowledger` (`amqp091.Delivery`'s own `Acknowledger` interface field) so `msg.Ack`/`msg.Nack` can be observed without a real channel. Both guarded with a `sync.Mutex` (written from the `messaging.Run` goroutine, read from the test goroutine); assertions use a polling `waitFor(t, timeout, cond)` helper rather than a fixed `time.Sleep`, since the retry path's `time.Sleep(retryCount+1 seconds)` makes a fixed wait either flaky or slow.

**Truncating just `restaurants` is enough, even for pizza-related tests**: `TestDB.TruncateTables` uses `TRUNCATE ... CASCADE`, which cascades along FK edges regardless of each FK's own `ON DELETE` setting — `db.TruncateTables(t, testutil.TableRestaurant)` alone also clears `pizzas`/`pizza_prices`/`topping_prices`/`payout_details`. A pizza's toppings live inside the `pizzas` row itself, so there's nothing extra to truncate for those. No `TablePizza`/`TablePizzaPrice`/`TableToppingPrice` constant in `testutil/db.go`, and there shouldn't be one. `pizza_sizes`/`toppings` are global catalogs seeded once by migrations and never truncated between tests.
