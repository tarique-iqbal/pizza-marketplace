# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Scope: this file covers `order-service` only. See the root `CLAUDE.md` for monorepo-wide architecture and how this service fits into the event flow, and `docs/services/order-service.md`/`docs/api/order-service.md` for the full technical writeup this file summarizes.

## What this service owns

The customer-facing basket (`Cart`) and the `Order` aggregate: adding items, checking out, and driving payment via a separate `payment-service` over gRPC. Owns its own Postgres database and runs the transactional outbox pattern, same as identity-service/restaurant-service. Keeps a local read-model of restaurant/pizza/pricing data fresh by consuming restaurant-service's events off RabbitMQ (never importing restaurant-service's Go types) rather than calling it synchronously — the same pattern search-service uses.

Routes (behind Traefik, no `jwt@docker` label — auth enforced per-route-group in Gin instead, same as search-service):
- `GET`/`POST`/`PATCH`/`DELETE` `/cart`, `/cart/items[/:itemId]` — any authenticated user, no role gate (an `owner` account can place an order too; see `Middleware.Auth` only, no `RequireRole`). No `DELETE /cart` (clear-whole-cart) endpoint exists.
- `POST /orders` — checkout: converts the current cart into an `Order`, revalidates every line against live prices/availability, checks fulfillment support and minimum order, geocodes+validates the delivery radius, then calls payment-service for a real checkout URL. See `internal/application/order/commands/checkout.go`.

## Commands

Run from inside `order-service/`:
```bash
go run ./cmd/api      # HTTP API (or `air -c .air.toml` for live reload, matches the dev container)
go run ./cmd/worker   # RabbitMQ consumer (restaurant.events/identity.events/payment.events) + outbox relay
go test ./...
go test ./... -run TestName
```
Tests are integration-style against real Postgres (see root `CLAUDE.md` for `compose.test.yaml`); no mocked-DB path for anything touching a transaction. Needs `.env.test` populated like `.env.example` (`POSTGRES_*`, `RABBITMQ_URL`, `OPENCAGE_API_KEY`, `PAYMENT_SERVICE_ADDR`, `FRONTEND_BASE_URL`).

## Architecture specifics

- **`cmd/worker` runs two goroutines side by side**: a RabbitMQ consumer and an outbox relay, same shape as restaurant-service. The consumer's `Exchanges` map (`internal/infrastructure/messaging/rabbitmq_consumer.go`) has three keys — `restaurant.events` (4 read-model sync routing keys), `identity.events` (`user.registered`, syncs the local `customers` table), and `payment.events` (`payment.succeeded`/`payment.failed`, closes the payment saga — see below). All three land on the same `readmodel.EventDispatcher`, registered by literal routing-key string in `internal/container/worker.go`.
- **The local read-model (`internal/domain/readmodel/`) is a deliberate 4-table duplication of restaurant-service's own data** (`restaurants`, `pizzas`, `pizza_prices`, `topping_prices`, plus a `customers` mirror from identity-service) — considered and rejected calling search-service's `GET /search/restaurant/:id` instead, since that would introduce the first synchronous inter-service call on the checkout path. Every write is a redelivery/ordering-safe upsert (`ON CONFLICT ... WHERE updated_at < excluded.updated_at`, except `customers` which has no `updated_at` and uses plain `DoNothing`) — never trust event delivery order.
- **Order totals are always computed server-side from this read-model.** `Checkout`'s request body carries no price fields at all, only IDs and quantities — a `decimal.Decimal` field can't even carry a `go-playground/validator` numeric tag (panics on that type), so keeping prices off the wire entirely avoids the problem rather than working around it.
- **Cart is scoped to one restaurant at a time** (`carts.customer_id UNIQUE`) — adding an item from a different restaurant than the cart's current one returns `409` rather than silently clearing the cart. `AddOrMergeItem` is a Postgres upsert keyed on `(cart_id, pizza_id, size_id, extra_toppings)` — the same pizza+size+topping combo added twice increments quantity instead of duplicating a line. No price is ever stored on a `CartItem`; `GET /cart` resolves every line's current price/availability fresh on every call and flags `available: false` rather than silently dropping an archived item.
- **`Checkout` (`internal/application/order/commands/checkout.go`) is the one command threading a raw `*gorm.DB` across two repositories** (`cart.CartRepository`, `order.OrderRepository`) via `WithTx` — one transaction creates the `Order`+`OrderItems` and clears the cart; the payment-service gRPC call happens *outside* that transaction (a network call shouldn't hold DB locks open), and a `payment_id` is recorded with a separate `UPDATE` afterward.
- **Delivery-address re-validation is Postgres-backed, not live-geocoded on every checkout**: `internal/infrastructure/geocoder/caching_geocoder.go` decorates a raw `OpenCageGeocoder` (order-service's own independent OpenCage client/quota) with a cache keyed by SHA-256 of normalized address parts (`internal/shared/geo/address_hash.go`), mirroring search-service's Elasticsearch-backed cache but on Postgres. No TTL — street coordinates don't change. `geo.HaversineKm` gates the delivery-radius check; geocoder failures fail closed (`503`), never silently skip the check.
- **Payment is a gRPC call to a separate `payment-service`, wrapped in a circuit breaker** — `internal/infrastructure/payment/grpc_client.go` (`Client`, implements `order.PaymentProvider`, plaintext gRPC, internal network only) decorated by `circuit_breaker.go` (`CircuitBreakerProvider`, two independent `sony/gobreaker/v2` breakers — one per method, since `CreatePayment`/`CancelPayment` return different types — 5 consecutive failures trips, translates a breaker-open error to `order.ErrPaymentServiceUnavailable` rather than leaking a `gobreaker`-specific type). The generated pb client code (`internal/infrastructure/payment/pb/`) is copied by hand from payment-service's own `internal/interfaces/grpc/pb/` — no shared Go module between services, kept in sync manually.
- **The payment saga closes asynchronously, never synchronously**: Mollie's webhook goes to payment-service, not here, so order-service only learns a payment outcome by consuming `payment.succeeded`/`payment.failed`. `PaymentSucceededHandler`/`PaymentFailedHandler` (`internal/application/order/handlers/`) load the order by the event's `subject_id`, call `Order.Confirm()`/`Cancel()`, and (on confirm) dispatch `order.confirmed` via `orderapp.DispatchEventsTx` — this service's first domain event needing outbox dispatch at all, since `Checkout` itself never raises one (no speculative `order.placed`). Both handlers treat `order.ErrInvalidStatusTransition` as an idempotent no-op — Mollie retries its webhook for up to ~26h, and RabbitMQ redelivery must never double-confirm/double-cancel.
- **`OrderConfirmedPayload` is built via an `Enricher` closure, not looked up inside it**: the restaurant-name/owner-email lookup happens *before* the closure is constructed (a real, propagated error if it fails), since the `Enricher` signature (`func(DomainEvent) (event.Event, bool)`) has no error channel — a fallible lookup inside the closure itself could only fail by silently dropping the event.
- **Order lifecycle is 5 states**, not the originally-planned 6: `pending → confirmed → ready → completed`, plus `cancelled` (valid from `pending`/`confirmed`). No `preparing` stage — the `status` column already records "currently preparing" without needing a separate timestamp/transition.
- **Error convention**: shared-sentinel pattern like every other service — `internal/shared/errors` plus domain-specific errors in `internal/domain/{order,cart}/errors.go`; `response.HandleError` owns the HTTP status per error, including `order.ErrGeocodingUnavailable`/`order.ErrPaymentServiceUnavailable` (both `503`).
- **`Money` (`internal/shared/money`)** exists for the same reason as restaurant-service's own: `decimal.Decimal.MarshalJSON()` trims trailing zeros (`1.50` → `"1.5"`). Domain/persistence layers keep plain `decimal.Decimal`; `Money` wraps only at the response boundary.

## Testing conventions

Same shape as restaurant-service: `tests/` mirrors `internal/`, `tests/testutil/db.go` gives a real GORM `TestDB` + table truncation, `tests/infrastructure/db/fixtures/*.go` provide `LoadXFixtures(t, db)` helpers. **Any command or handler using `db.Transaction`/`WithTx` is tested against real Postgres, never mocked repositories** — a fake can't validate real transactional/rollback behavior (`Checkout`, `PaymentSucceededHandler`, `PaymentFailedHandler`); only genuinely external dependencies (`Geocoder`, `PaymentProvider`) get local fakes defined in the test file itself. Commands that don't touch a transaction (`AddItem`, `UpdateItemQuantity`, `RemoveItem`, `GetCart`) use `tests/testutil.Mock*Repository` fakes instead.

The gRPC client (`tests/infrastructure/payment/grpc_client_test.go`) is tested via `google.golang.org/grpc/test/bufconn` — this repo's first use of bufconn — against a small in-memory `pb.PaymentServiceServer` stub, no real network listener and no real payment-service. The circuit breaker (`tests/infrastructure/payment/circuit_breaker_test.go`) is tested against a local fake `PaymentProvider`, no gRPC involved — these tests verify the integration logic, not `gobreaker`'s own state-machine timing.
